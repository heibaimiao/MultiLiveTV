# 影视多源采集与多线路聚合产品文档

- 产品：MultiLiveTV
- 版本：V1
- 日期：2026-09-04
- 状态：目标规格（对照当前实现见第 13 节）
- 来源：ChatGPT 分享讨论整理，并对照仓库现有聚合能力改写
- 现状清单：[01-product.md](01-product.md)
- 法律约束：仅供个人学习研究；不绕过会员、DRM 或未授权内容保护

本文回答一件事：用户只看到「一部片、若干线路」，系统如何把不同采集站、不同字段、不同播放地址收成这一条体验。

---

## 1. 背景与问题

采集站之间没有统一契约。同一部影片会同时出现这些情况：

| 现象 | 例子 |
| --- | --- |
| 采集方式不同 | MacCMS JSON / XML、脚本站、解析站 |
| 分类 ID 不互通 | 源 A 的 `type_id=1` 是电影，源 B 的 `1` 是国产动漫 |
| 字段名字不同 | `vod_name` / `title` / `name` |
| 片名写法不同 | 庆余年 / 庆余年第一季 / 庆余年(2024) |
| 同名不同片 | 《神话》2005 电影 vs 2010 电视剧 |
| 同名不同年 | 《封神》2023 / 2024 / 2025 |
| 单源缺字段 | 有海报没演员，有演员没简介 |
| 线路质量不稳 | 有的 403、有的超时、有的集数不全 |

如果 App 直接展示各源原始数据，用户会看到重复卡片、错分类、错合并和不可播线路。

产品要解决的不是「把所有线路塞进 App」，而是建立统一资源模型。

---

## 2. 产品定位

MultiLiveTV 不是自建片库，也不是内容分发平台。

- **输入：** 多个第三方采集源
- **处理：** 适配 → 标准化 → 同片识别 → 字段补齐 → 线路聚合
- **输出：** 统一分类、统一搜索结果、统一详情、可排序的播放线路

App 只理解这条链路：

```text
搜索 / 分类
  → 影片（Unified Media）
    → 播放
      → 线路（Route）
        → 播放地址
```

采集协议、脚本类型、原始字段全部藏在 Provider 之后。

### 2.1 第一版部署形态

第一版**不强制**自建后端网关。仓库当前是双路径：

| 端 | 形态 |
| --- | --- |
| Apple | 本地 Source Engine，直连采集站 |
| Go API / Android / Admin | 服务端聚合，客户端只消费统一结果 |

两条路径必须遵守同一套产品模型：同一分类 slug、同一合并规则、同一线路形状。不允许两端「看起来像同一产品、合并结果却不同」。

---

## 3. 核心原则

1. **源头可以乱，出口必须干净。** 源站分类、字段、ID 都不进入 UI。
2. **片名只是搜索入口，不是影片 ID。** 真正身份是 `mediaId`（标准标题 + 年份 + 类型 + 季数等）。
3. **少合并优于错合并。** 把两部不同影片合成一条，比漏合一条更糟。
4. **采集源 ≠ 播放线路。** 一个源可以贡献多条线路；一条线路也可以来自解析站。
5. **按字段补齐，不按整源覆盖。** 海报可以来自 A，演员来自 B，播放来自 C。
6. **缺字段不能凭空编。** 一个接口没给的数据，只能向其他源或元数据源补；补不到就显示缺失。
7. **第一版只保证 CMS 采集。** JS / Python 脚本 Provider 可以预留接口，不作为 V1 必达。

## 4. 核心概念

必须先分清三层，不能混用。

### 4.1 Source（采集源）

负责提供目录与详情，例如资源站 A / B / C。

能力可以是：搜索、分类列表、详情、剧集、播放引用。某个源可以缺少分类，但不能没有「能被搜到或被列到」的入口。

### 4.2 Provider（采集方式）

Source 的接入协议。V1 定义五类，**只实现前两类为必达**：

| Provider | 说明 | V1 |
| --- | --- | --- |
| CMS API | 苹果 CMS / 海洋 CMS 等 JSON、XML | 必达（当前主路径） |
| Parse | 把播放页解析成可播地址（`jx_url`、ticket） | 必达 |
| Aggregate | 多源并发搜索后再合并 | 必达（搜索/分类/详情都走它） |
| JS Script | 站点脚本运行时 | 预留，不在 V1 |
| Python Script | `api = xxx.py` 一类脚本 | 预留，不在 V1 |

统一调用形状（对内，不暴露给 UI）：

```text
search(keyword)
list(category, page)
detail(id)
play(id)
```

### 4.3 Route（播放线路）

用户在详情页看到的「线路 A / 线路 B」。它挂在 Unified Media 下面，而不是挂在某个 Source 名称下面。

```text
Source A
  ├── 普通线路
  └── 高清线路
Source B
  └── 默认线路
        │
        ▼
庆余年
  ├── 线路 A
  ├── 线路 B
  └── 线路 C
```

### 4.4 两级 ID

| 级别 | ID | 作用 |
| --- | --- | --- |
| 产品实体 | `mediaId` | 一部确定的影视作品 |
| 源站实体 | `sourceId` + `originalId` | 某站自己的影片编号 |

例如：

```text
mediaId = media_庆余年_2024_s1
  ├── 源 A / 12345
  ├── 源 B / 98765
  └── 源 C / abc123
```

## 5. 用户场景与界面

用户感知的是「一部片」，不是「一个采集站」。

### 5.1 搜索

用户搜「庆余年」。

**不要显示：**

- 庆余年
- 庆余年第一季
- 庆余年 2024
- 庆余年电视剧

**要显示：** 每个独立作品一张卡。

```text
┌──────────────────────────┐
│ [海报]  庆余年            │
│ 2024 · 电视剧 · 36 集     │
│ 8 个播放源                │
└──────────────────────────┘

┌──────────────────────────┐
│ [海报]  庆余年 第二季      │
│ 2024 · 电视剧             │
│ 5 个播放源                │
└──────────────────────────┘
```

同名不同作品必须拆卡，例如：

```text
倚天屠龙记 · 2026 · 电影     5 个播放源
倚天屠龙记 · 2003 · 电视剧   8 个播放源
```

### 5.2 分类浏览

首页一级分类由产品定义，不展示源站原始分类名。当前已落地的一级：

- 全部
- 电影
- 剧集
- 综艺
- 动漫
- 短剧

进入某一分类后，跨源拉列表，再按同片规则合并。用户不应看到「影片 / 连续剧 / 卡通」这种源站别名并列。

### 5.3 详情

```text
庆余年
2024 · 电视剧 · 36 集

简介……
导演 / 演员 / 地区

播放线路（已按可用性排序）
[线路 A] [线路 B] [线路 C]

线路 A
[01] [02] [03] …
```

选某一集时，可在该集下切换线路。缺集的线路不得把空位伪装成可播。

### 5.4 播放失败

当前线路失败时，自动尝试下一条健康线路；用户可手动改线。不把失败原因展示成技术堆栈，提示「该线路暂不可用，已切换」即可。

## 6. 功能需求

### 6.1 采集源管理

- 以配置注册 Source（id、名称、类型、地址、启用状态）。
- 未启用或 `vip_only` 的源不进入公开浏览。
- 单源失败不得拖垮整次搜索 / 分类 / 详情。
- 管理后台可增删改源并做连通测试（已有）。

### 6.2 数据标准化（Normalizer）

原始 JSON/XML 不得直接进 UI。先抽出：

| 内部字段 | 从源字段归一 |
| --- | --- |
| originalTitle | 源站原始片名 |
| canonicalTitle | 去掉空格、括号噪音、清晰度、语种标签后的标准名 |
| year / season / version / language | 从标题或独立字段解析，并保留下来 |
| type | 电影 / 剧集 / 综艺 / 动漫 / 短剧 等 |
| poster / description / directors / actors | 海报、简介、演职人员 |
| episodes | 标准化集数 |

标题清洗要处理：空格、括号、特殊字符、年份、`S01` / 第 01 季 / 第一季、高清 / 4K / 1080P、国语 / 粤语。

**不能简单全部删掉。** 第一季 vs 第二季、导演剪辑版、重制版代表不同实体，必须保留在 Identity 里。

### 6.3 同片识别（Media Matcher）

见第 8 节。搜索、分类列表、详情补源都走同一套 Matcher。

### 6.4 分类映射（Category Mapper）

见第 9 节。源站分类 → 产品分类；地区 / 类型标签拆维，不把「国产」当成一级品类。

### 6.5 字段级合并

见第 10 节。详情页每个展示字段都有来源与完整度。

### 6.6 线路聚合与取播

- 多源 `vod_play_from` / `vod_play_url` 拆成统一 `playSources`。
- 按权重排序；后续叠加健康分。
- 取播统一为 `direct`（直链 / jx）与 `ticket`（服务端解票）两种 mode。
- 客户端不持有解票密钥。

### 6.7 剧集对齐

不同源的「第 1 集 / 01 / EP01 / 第 01 话」对齐到 `episodeNumber`。用户点第 02 集时，看到的是该集下的多线路，而不是三套互不相干的集数条。

## 7. 统一数据模型

### 7.1 Unified Media（用户看到的一部片）

```text
Media
├── identity
│   ├── mediaId
│   ├── canonicalTitle
│   ├── year
│   ├── type
│   └── season
├── metadata
│   ├── title / poster / backdrop / description
│   ├── directors / actors / genres / region / language
│   └── completeness
├── metadataSources[]          每个字段来自哪个源
├── sourceItems[]              各采集站原始条目
└── playSources[]              面向播放的线路
```

`year` 不只是展示字段，它参与「是不是同一部」的判断。

### 7.2 Source Item（源站条目）

```json
{
  "sourceId": "164",
  "sourceName": "资源站A",
  "originalTitle": "庆余年第一季",
  "originalId": "12345",
  "provider": "cms_json",
  "episodes": []
}
```

### 7.3 Play Source（线路）

对外契约与现有统一线路模型对齐：`key`、`label`、`weight`、`mode`（`direct` | `ticket`）、`playFrom`、`sourceId`、`url` / `ticket`、`episodes[]`。

内部可以继续叫 PlaySource；产品层统一叫「线路」。

## 8. 同片识别规则

片名不能当唯一键。Matcher 在标准化之后打分。

### 8.1 覆盖的冲突类型

| 情况 | 处理 |
| --- | --- |
| 名字不同，实际同片 | 庆余年 / 庆余年第一季 / 庆余年(2024) → 合并 |
| 名字一样，年份不同 | 封神 2023 / 2024 / 2025 → 拆开 |
| 名字一样，作品不同 | 神话 2005 电影 vs 2010 电视剧 → 拆开 |
| 名字和年份都像，演职人员不同 | 同名同年底层不同片 → 拆开 |
| 同一作品多源 | 挂到同一 `mediaId`，线路并列 |
| 季数不同 | 第一季 / 第二季 → 不同 Media |
| 电影 vs 电视剧同名 | 类型不一致则倾向拆开 |
| 重制版 / 导演剪辑版 | `version` 不同则拆开 |
| 国语 / 粤语 | 默认视为同一 Media 的版本差异，挂在线路或 language 上，不拆成两部；若导演、年份、类型也不同则仍拆开 |

### 8.2 标题标准化

先得到 `canonicalTitle` + `season` + `year` + `version`。

年份缺失时不要直接判为三部：进入「标题匹配 → 年份校验 → 演员 / 类型 / 集数」的后续链路。源站年份经常不准，年份是强信号，不是唯一否决票。

### 8.3 评分（V1）

| 条件 | 分 |
| --- | --- |
| 标准标题 | 30 |
| 年份 | 20 |
| 类型 | 15 |
| 导演 | 15 |
| 主演 | 10 |
| 集数 | 5 |
| 国家 / 地区 | 5 |
| **总分** | **100** |

阈值：

| 分数 | 动作 |
| --- | --- |
| ≥ 85 | 自动合并 |
| 60–84 | 疑似同片，V1 **不自动合并**（可在详情「更多版本」露出） |
| < 60 | 不同影片 |

只有标题相同、其余全空时，分数约为 30，**绝对不能合并**。

### 8.4 硬规则（先于打分）

满足任一条则直接拆开，不再依赖总分：

- 标准标题相同，但季数明确不同（S1 vs S2）
- 类型明确冲突（电影 vs 电视剧），且导演或主演无明显交集
- 年份相差 ≥ 2 且主演集合无交集

### 8.5 当前实现差距

现网 `BuildVodMergeKey` 只做标题去空白与标点后的字符串相等。这能合并「庆余年」与「庆余年」，也会把同名不同片合成一条。V1 产品要求用本节规则替换该键。

## 9. 分类体系

### 9.1 原则

App 不显示源站分类。源站 `type_id` 只用于回源拉列表。

产品自己维护一套 **App Category**，通过 Category Mapper 把各源映射过来。

### 9.2 V1 一级分类

与现网 `unified-categories.json` 对齐：

- 电影 `movie`
- 剧集 `tv`（别名：电视剧、连续剧）
- 综艺 `variety`
- 动漫 `anime`
- 短剧 `short`

「纪录片 / 少儿 / 体育 / 音乐 / 其他」可进二级或「其他」，不挤占一级 Tab。

### 9.3 多维，而不是一个 category

源站的「国产 / 日韩 / 欧美」常常是地区，不是品类。

| 维度 | 例子 |
| --- | --- |
| type | 电影、剧集、综艺、动漫 |
| region | 中国大陆、香港、台湾、韩国、日本、欧美 |
| genre | 动作、喜剧、爱情、科幻 |
| year | 2026、2025 |
| language | 国语、粤语、日语 |

V1 首页只按 type 浏览；region / genre 作为详情标签与筛选预留，不把「国产」做成与「电影」平级的一级 Tab。

### 9.4 无分类的源

只有搜索、没有分类接口的源：不出现在分类浏览的 fan-out 里，仍参与搜索与详情补源。

### 9.5 映射维护

映射表可静态配置，脚本可从各源 `class` 刷新。不要把别名写死在业务代码里。已有别名示例：电视剧 → 剧集、影片 / 电影片 → 电影、卡通 / 日本动漫 → 动漫。

## 10. 字段合并与完整度

一个接口缺字段，不能靠它自己补全。系统采用：

> 多源取数 + 字段级合并 + 来源优先级 + 缺失字段继续补采 + 播放源独立聚合

### 10.1 每个字段记住来源

内部不是只存 `poster = url`，而是 `value + sourceId`。海报错了才能追到是哪个站。

### 10.2 冲突时不整源覆盖

不同字段可以有不同优先级。例如海报认 A、简介认 B、演员认 C。优先级表可配置，默认规则：

| 字段 | 选取 |
| --- | --- |
| 海报 | 先有图者优先，其次源权重 |
| 简介 | 更长且非空者优先 |
| 导演 / 演员 | 更完整名单优先；明显乱码或过短的丢弃 |
| 年份 / 类型 | Matcher 已采用的 Identity 为准，展示层不反写 |
| 剧集列表 | 集数更全者作为主列表，其它源按集号挂线路 |
| 播放地址 | 永不互相覆盖，只追加为线路 |

### 10.3 完整度

每部 Media 计算 `completeness`（标题、年份、海报、简介、导演、演员、类型、地区、评分、剧集是否有值）。

补采策略：

```text
请求 Source A
  → 已有标题 / 海报 / 年份 / 剧集
  → 缺导演、演员、简介
请求 Source B 只补缺失字段
  → 完整度 ≥ 90% 则停止
```

禁止为了补字段把全部源打一遍。完整度 < 50% 才继续找源；≥ 90% 停止。V1 详情补源上限与现网一致：最多再搜 16 个标题变体。

### 10.4 元数据源（可选，非 V1 必达）

播放源与元数据源可分开：采集站主责剧集与播放，第三方 Metadata Provider 主责海报 / 简介 / 演职人员。V1 先在已有采集站之间补齐；独立 Metadata Provider 放到后续。

## 11. 播放线路

### 11.1 展示

详情页展示的是线路，不是源站列表。源站名称可以做次要标注（「来自 xx 站」），不能当主 Tab。

### 11.2 排序

V1 已有静态权重表（`play-line-weights.json`）。产品目标排序键：

1. 健康分（可用率、最近成功率）
2. 配置权重
3. 延迟

用户上次成功播放的线路可置顶（需账号或本地记忆；现网客户端尚未统一）。

### 11.3 健康检查（V1 可简化）

对 Source / Route 记录：成功、延迟、上次成功、上次失败，合成 `healthScore`。连续失败的线路沉底或暂时隐藏。

V1 最低要求：单源超时或 HTTP 失败则跳过，不阻塞其它源；不必上独立巡检服务。

### 11.4 取播

| mode | 含义 |
| --- | --- |
| direct | 已是媒体 URL，或经该源 `jx_url` 解析 |
| ticket | 服务端持有密钥，向 bpz5 一类接口解票后返回短时 URL |

密钥、HMAC、session 不出客户端。无法合法得到的受保护流，产品不提供绕过方案。

## 12. 性能与容错

### 12.1 并发

搜索 / 分类 / 详情补源必须并发，禁止按源串行。现网分类列表最多 8 路并发，可保持。

### 12.2 缓存（建议）

| 缓存 | TTL |
| --- | --- |
| 搜索结果 | 5–15 分钟 |
| 详情 | 30–60 分钟 |
| 分类列表 | 现网已有分类树缓存，保持 |
| Matcher 结果 | 与详情同级 |
| 线路健康 | 1–5 分钟 |

### 12.3 错误隔离

某个 Provider 抛错，只标记该源失败（`sourcesFailed`），其余源结果仍返回。全部失败时列表可为空，但搜索/分类接口仍成功返回，由 UI 展示空态。

## 13. 与当前实现对照

| 能力 | 现状 | 本文要求 |

## 16. 成功标准

满足以下条件，才认为聚合体验达标：

1. 搜索「庆余年」不会列出 4 张仅文案不同的重复卡；季数不同仍拆卡。
2. 搜索「神话」至少拆出电影版与电视剧版，不会把成龙与胡歌合成一部。
3. 搜索「倚天屠龙记」按年份 + 类型拆卡，同版本下只出现线路切换。
4. 打开详情，缺简介或演员时会从其它源补上，而不是整页空白或整源覆盖成另一部片。
5. 用户选线播放失败后能换到下一条，不必返回列表重进。
6. 首页分类只有产品定义的一级，不出现「影片 / 连续剧 / 卡通」并列。

## 附录 B. 决策记录

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 要不要先做公共 API | 不强制；Apple 可本地，Go 可服务端 | 个人/小规模下先跑通模型，比先上中台更重要 |
| 疑似同片 | V1 不自动合并 | 错合并的伤害大于漏合并 |
| 分类模型 | 静态统一表 + 映射 | 已在现网验证；动态猜分类不稳定 |
| 脚本源 | V1 不做 | 运行时复杂，且与合法边界更近 |
| FGBLH | 仅作配置输入，不当架构 | 那是线路仓库，不是产品内核 |
